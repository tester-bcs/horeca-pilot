## Апстрим: канонический tester-bcs/luck (доступ на запись — denisg0mes, tester-bcs)

- [ ] **RFC: слот `EXPECT` у SPAWN** — объявление ICOM ожидаемого подграфа,
      например `EXPECT (produces=<ident>, consumes=<ident,...>)`.
      Зачем: сейчас у SPAWN есть гарантия синтаксиса (constrained decoding) и
      гарантия объёма (max_depth/max_nodes), но НЕТ гарантии релевантности —
      подграф может быть каноничным, уложиться в бюджет и решать не ту задачу.
      Без слота правило ICOM-баланса «подграф обязан произвести обещанный
      родителем выход» непроверяемо в принципе: `PLAN` — свободный текст,
      `INTO` принимает текст плана, а не результат подграфа.
      Обоснование и разбор — [docs/ICOM-VALIDATOR.md](docs/ICOM-VALIDATOR.md).
      Осторожно: слот меняет реестр типов узлов, из которого выводятся EBNF,
      правило разбора, таблица совместимости, порядок слотов для cache_key и
      грамматика decoding. Отдельно решить, входит ли слот в `cache_key`
      (если да — обнуляются ключи всех существующих SPAWN-узлов).
      Порядок: RFC → решение владельца репо → реализация тем, у кого доступ.
- [ ] После `EXPECT`: нарушения `icom::validate_spawned` → `reject`-узлы.
      Только они: по SPEC («Границы обработки ошибок») reject уместен, когда
      граф уже существует. Нарушения проверки МОДЕЛИ под reject не подходят —
      графа в этот момент ещё нет, они обязаны оставаться списком.
