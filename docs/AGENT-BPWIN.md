# Агент-BPWin: мета-технология «обследование → работающий пайп»

## Суть

Клиент пайпа (предприятие) НЕ рисует диаграммы. Клиент отвечает на вопросы
агента-обследователя, агент строит IDEF0-модель (функциональные блоки ICOM),
клиент подтверждает, и модель АВТОМАТИЧЕСКИ превращается в исполнимый Luck-план.

## Ядро: «функциональный блок» (одна декларация — все производные)

```
Блок = { id, функция, ICOM (inputs/controls/outputs/mechanisms),
         природа (step/tool/classify/verify/branch), декомпозиция (children) }
```

Из блока выводятся: IDEF0-диаграмма (презентация), Luck-узел (исполнение),
документы (форма), VERIFY-предикаты (контроль), вопросы интервью (разговорник).

## Маппинг ICOM → Luck (реализовано в src/idef0.rs)

| IDEF0 | Luck |
|---|---|
| Function | NODE (kind: step/tool/classify/verify/branch) |
| Input/Output | потоки: INPUT/INTO, рёбра по соответствию имён |
| Control | рёбра-управления; VERIFY-предикаты (v2) |
| Mechanism | TOOL-имя (v2) |
| Декомпозиция | children (v2: SPAWN-подграфы) |
| A-0 контекст | рамка, НЕ исполняется — исполняется декомпозиция |

Правило ребра: если output(A) ∈ inputs(B) или controls(B) → ребро A→B.

## Ограничение (честно)

IDEF0 выражает ФУНКЦИИ и ПОТОКИ, но не РЕШЕНИЯ. Ветвление (BRANCH) в IDEF0
не выражается — добавляется на этапе Luck-графа (вручную или классификатором).
Это не баг методологии, а её граница: IDEF0 отвечает «из чего состоит система»,
не «как система принимает решения».

## Мета-бустрап

Сам процесс обследования — Luck-план: узлы = этапы интервью, VERIFY = «модель
полна (нет пустых блоков, все стрелки замкнуты)», ветки = «есть склад? есть
производство?». Движок, который исполняет бизнес, сам проводит обследование.

## Как устроен интервью-агент (`luck-pilot/src/interview.rs`)

Ключевое решение — **разделение «что спросить» и «как понять ответ»**:

| | Кто решает | Почему так |
|---|---|---|
| ЧТО спросить дальше | код, детерминированно | `next_question` — чистая функция от состояния модели; ход обследования задают нарушения валидатора `icom` |
| КАК понять ответ | LLM | единственная её роль: свободный текст клиента → структура `Block` |

Обратный порядок (LLM ведёт опрос, код записывает) отвергнут сознательно: тогда полнота
обследования зависела бы от того, догадалась ли модель спросить. А так порядок вопросов
воспроизводим, тестируется без сети и не зависит от того, какая LLM подключена.

**Контур обследования.** Модели нет → спрашиваем рамку A-0. Рамка есть, шагов нет →
спрашиваем шаги. Дальше вопрос выводится из первого нарушения валидатора (сначала ошибки,
потом предупреждения), и каждому правилу соответствует деловая формулировка — клиент не
обязан знать слов «ICOM» и «декомпозиция»:

```
DanglingInput   → «Шагу A3 нужно "накладная", но никто этого не производит.
                   Откуда это берётся?»
MissingOutput   → «Итог процесса — "отчёт", но ни один шаг его не формирует.»
Cycle           → «Шаги ждут результатов друг друга по кругу. С какого работа начинается?»
OrphanBlock     → «Шаг ни с чем не связан. Куда он встраивается — или его убрать?»
```

Нарушений нет → `Confirm`: модель показывается клиенту на подтверждение и готова к
`map_to_graph_checked`.

**Две защиты от порчи модели.** Правка, добавляющая новых ошибок больше, чем убирает,
откатывается — иначе разговор ходит по кругу, а модель с каждым ответом становится дырявее.
Ответ, не разобравшийся в JSON, даёт внятную ошибку и не меняет модель вовсе.

**Проверка.** Ядро — юнит-тестами без сети; весь разговор целиком — `tests/interview_e2e.rs`
на скриптованном транспорте: рамка → шаги с намеренным пробелом → агент сам замечает
пробел и спрашивает именно про него → правка → `Confirm` → модель проходит валидатор,
компилируется в граф и исполняется планировщиком.
