# Технические детали horeca-pilot

Архитектура (с 2026-08-12): `luck-pilot/` — тонкая HoReCa-обвязка вокруг
вендорного канонического движка Luck (`luck-pilot/vendor/luck-engine/`,
крейт `luck`, происхождение — [tester-bcs/luck](https://github.com/tester-bcs/luck)).
Обвязка: IDEF0-маппер (`idef0.rs`), рантаймы OpenRouter/Ollama (`openrouter.rs`,
на базе вендорского `anthropic::ChatTransport`/`ValidatingBackend`), бизнес-VERIFY-
предикаты HoReCa (`verify.rs`). Сценарии: `examples_luck/*.luck` — канонический
синтаксис Luck (см. апстрим README/SPEC), не старый диалект luck-pilot v0.1.

## Миграция v0.1 → v0.2 (2026-08-12): переход на канонический движок

До 2026-08-11 `luck-pilot` был самостоятельным ad hoc форком с собственным
`plan.json`-IR (`luck_plan.rs`/`luck_compile.rs`/`luck_scheduler.rs`, 12 типов
узлов включая отдельные `BRANCH`/`MERGE`/`VERIFY`-узлы). Апстрим Luck тем временем
консолидировался: Python-исследовательский репозиторий `tester-bcs/luck-lang`
архивирован и слит в канонический `tester-bcs/luck` (язык + Rust-рантайм,
POLICY/VERIFY/BUDGET перенесены и на Rust-сторону). Решение: вендорить канон
вместо поддержки параллельной неполной реализации, все три старых модуля
удалены, вся Luck-специфика теперь приходит из `vendor/luck-engine`.

Каноническая модель отличается от старой не только именами типов:

- **9 типов реестра** (`ROLE, TASK, FILTER, STEP, CLASSIFY, SPAWN, TOOL,
  DOCUMENT, REJECT_MARK`) — без отдельных узлов `BRANCH`/`MERGE`/`VERIFY`.
- **BRANCH** — не узел, а свойство ребра: `EdgeType::Branch` (`=>`) с меткой
  `[label]`. Условие активации (`scheduler.rs::edge_is_active`): ребро активно,
  если исходный узел исполнен И его **фактический текстовый вывод** (не алиас
  из `LABELS`!), нормализованный (`trim().to_uppercase()`), совпадает с
  `normalize_label(label)`.
- **MERGE** — не узел, а тип ребра `EdgeType::Merge` (`~>`): активация по ЛЮБОМУ
  исполненному предку (OR), а не по всем (AND, как у `Seq`). Обычный узел с
  входящими `~>`-рёбрами от обоих хвостов ветвления — и есть точка слияния.
  ВАЖНО: нельзя смешивать на одном узле входящие `Branch`- и `Merge`/`Seq`-рёбра
  от разных предков — группы комбинируются по И, а на границе слияния нужна
  чистая ИЛИ-семантика; поэтому оба хвоста ветвления сведены к единому типу
  ребра (`~>`) в точку слияния.
- **VERIFY/POLICY/BUDGET** — необязательные *слоты* на любом узле
  (`VERIFY checker="имя"`), не отдельные узлы. Вендор их парсит, но **не
  проверяет** — enforcement живёт в `luck-pilot/src/verify.rs`
  (`run_verified`, обёртка над `Scheduler::run`, пост-хок проверка после
  прогона). Соглашение luck-pilot (не часть грамматики): `subject="узел"` —
  чей вывод проверяется; по умолчанию — собственный вывод узла.

### Питфолл, обожжённый на миграции: `LABELS`-алиас ≠ метка ребра

Грамматика `LABELS ok="хватает", short="не хватает"` объявляет **алиас → значение**,
но модель обязана вывести именно **значение** (`"хватает"`), а не алиас (`"ok"`).
Метка на branch-ребре сверяется с фактическим выводом модели — значит писать в
скобках нужно значение (`stock_check => produce_ok [хватает]`), а не алиас
(`[ok]`). Все 4 сценария изначально были смигрированы с алиасами в скобках —
графы молча обрывались на 2–3 узлах (ни одна ветка не активировалась), но
`run` печатал `ГОТОВО`, потому что до `Reject` дело не доходило — просто
недостижимые узлы никогда не планировались. Обнаружено только на live-прогоне
(тесты на моках этого не ловят — не проверяют полноту прошедшего пути).

Второй нюанс: метка ребра — токен лексера (`is_alphanumeric() || '_'`, **без
пробелов**). Многословные значения `LABELS` (`"в пределах нормы"`) нельзя
использовать как метку ребра. Исправление: значения `LABELS` во всех 4
сценариях сделаны однословными (`"норма"`, `"отклонение"`, `"брак"`,
`"повреждение"`, `"просрочка"`, `"пересорт"`, `"нехватка"`, `"риск"`), метки
рёбер синхронизированы с ними.

## Мост «1+6 → Luck» (карта соответствия)

| Срез 1+6 | Конструкт Luck | Как |
|---|---|---|
| 1. Инвариант | ЦЕЛЬ пайпа + VERIFY-слот на критичных узлах | Инвариант = то, что пайп обязан не порвать; VERIFY checker="..." до разрыва |
| 2. Декомпозиция | Модули A1..AN → подграфы (SPAWN-вложенность) | Каждый модуль = свой .luck-файл/подграф; сборка = граф верхнего уровня |
| 3. Связи | EDGES с типами (`->` seq, `=>` branch, `~>` merge) | Материальный/денежный/информационный поток = ребро |
| 4. Форма | Слоты INTO/INPUT + VERIFY checker | Документ = форма потока; честность = VERIFY «документ существует и заполнен» |
| 5. Динамика | CLASSIFY → branch-рёбра `=>`, REJECT_MARK | Состояния = CLASSIFY-узлы; отказы = REJECT_MARK-узел графа (не исключение) |
| 6. Границы | Вход/выход графа | Узлы на границе = intake (вход) / report (выход) |

## VERIFY: бизнес-предикаты HoReCa (luck-pilot/src/verify.rs)

| Проверка | Предикат | Инвариант |
|---|---|---|
| Непустой вывод | not_empty | форма честна |
| Остаток ≥ потребность | stock_level — {stock, need} | И1 — сырьё не кончилось |
| Комплектация = заказ | order_match — {ordered, picked} | И4 — полнота |
| Кэш-прогноз ≥ обязательства | cash_ok — {cash, obligations} | И2 — нет кассового разрыва |
| Срок годности > горизонт | shelf_life_ok — {expires, horizon}, ISO-даты | И3 — скоропорт не портится |
| Температурный лог в норме | temp_log_ok — {temp, max} | И3 — режим хранения |
| Задолженность ≤ лимит | credit_ok — {limit, outstanding} | И2 — кредитный контроль |

Реализация — чистые функции, портированные почти без изменений из старого
`luck_scheduler.rs`; `run_verified()` в `verify.rs` прогоняет
`Scheduler::run`, затем пост-хок проходит по узлам с VERIFY-слотом и
проверяет их вывод (или вывод узла из `subject=`) через соответствующий
предикат.

## Сценарии (все 4 проходят граф целиком на live-прогоне)

1. `horeca-daily-cycle.luck` — дневной цикл: intake → plan → stock_check →
   `{хватает→produce_ok | нехватка→purchase→produce_short}` → pick (merge) →
   dispatch → bill → report.
2. `horeca-returns.luck` — возвраты/рекламации: 4 ветки по причине
   (брак/повреждение/просрочка/пересорт) → settle → отчёт.
3. `horeca-inventory.luck` — инвентаризация: freeze → count → compare →
   `{норма→write_off | отклонение→investigate→resolve}` → close → отчёт.
4. `horeca-cashflow.luck` — cash-прогноз + кредитный контроль: receivables →
   forecast → VERIFY cash_ok → `{норма→pay | риск→hold}` + credit_api →
   VERIFY credit_ok → settle_cash → отчёт.

## Выбор модели для live-прогона

Reasoning-модели (nvidia/nemotron-3-super-120b-a12b:free и подобные) тратят
токены на «раздумья» перед ответом — с `max_tokens` по умолчанию рискуют не
уложиться в лимит и обрезать содержательный ответ ещё до `RESULT:`-префикса;
также заметно медленнее (~30–40с на вызов даже на тривиальном промпте).
Рекомендация: недорогая instruct-модель без CoT-надстройки —
`google/gemini-2.5-flash` (проверено live, все 4 сценария проходят целиком,
единичный запуск — единицы секунд). Расход токенов в пайпе низкий (граф на
8–10 узлов, ответы по несколько сотен токенов) — на бюджет в единицы долларов
можно прогнать все сценарии много раз.

Также замечено (на hermes3:8b и на nemotron, не на gemini-2.5-flash):
модель иногда путает свой узел с предыдущим в истории графа и повторяет
чужой ответ вместо реакции на собственный `DO`/`INPUT`. Промпт вендора
показывает узлу полную историю предыдущих пар «узел → ответ» — на некоторых
моделях это провоцирует эхо. Известное ограничение промпт-паттерна вендора,
не специфика horeca-pilot.

## Как запустить

```bash
cd luck-pilot
cargo test                                               # 18 тестов (13 unit + 5 e2e)

```

## Известные ограничения (после миграции на канонический движок)

- `web.rs` потерял live-стриминг прогресса по узлам — вендорский `Scheduler`
  не даёт event-хуков, только финальный `ExecutionResult`; веб теперь
  показывает результат пост-хок.
- VERIFY — пост-хок проверка, не блокирует исполнение графа посреди прогона;
  отказ репортится как `Rejected` уже после того, как остальной граф прошёл.
- `FallbackTransport` (openrouter.rs) трактует фатальные ошибки OpenRouter как
  сигнал упасть на Ollama, а не прервать прогон — сознательное отклонение от
  вендорской семантики `InvalidModelOutput::fatal` (там fatal должен
  прерывать весь `run()`).
