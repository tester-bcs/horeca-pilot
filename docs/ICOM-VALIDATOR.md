# Валидатор ICOM-баланса

**Модуль:** `luck-pilot/src/icom.rs`. **CLI:** `cargo run --bin validate -- <model.json>`.
**Статус:** реализован, 9 тестов. Закрывает пункт «Валидатор полноты модели
(висячие стрелки, пустые блоки)» из `AGENT-BPWIN.md`.

## Зачем

Маппер `idef0.rs` строит рёбра по совпадению имён: `output(A) ∈ inputs(B) ∪ controls(B)`.
Из этого следует тихий режим отказа: **опечатка в имени потока не ломает ничего явно** —
ребро просто не строится, блок выпадает из графа, план исполняется без него. Клиент
подтверждает модель, которая выглядит правильной и таковой не является.

Проверка — классическое правило целостности декомпозиции IDEF0: граничные стрелки
дочерней диаграммы обязаны совпадать с ICOM родительского блока.

## Реализованные правила

| Правило | Уровень | Смысл |
|---|---|---|
| `MissingOutput` | ошибка | выход родителя не производится ни одним подблоком |
| `DanglingInput` | ошибка | вход/управление подблока не приходит ни извне, ни от соседа |
| `UnusedParentInput` | предупреждение | стрелка родителя никем не потребляется |
| `EmptyBlock` | ошибка | пустой id или пустая формулировка функции |
| `NoOutput` | предупреждение | терминальный блок без объявленного выхода |
| `BranchTargetMissing` | ошибка | ветка указывает на несуществующий блок |
| `BranchKindMismatch` | ошибка | ветки без `kind:"branch"` (или наоборот) |
| `DuplicateId` | ошибка | дубликат id — `map_to_graph` на нём паникует |
| `Cycle` | ошибка | цикл по данным — `Scheduler::run` вернёт Err |
| `SelfLoop` | ошибка | блок читает то, что сам производит (маппер петли пропускает) |
| `BranchConsumerUnlinked` | ошибка | читатель выхода branch-блока вне его веток остаётся без ребра |
| `DuplicateOutput` | предупреждение | один поток пишут несколько блоков — источник неоднозначен |
| `OrphanBlock` | предупреждение | блок вне потока: ни входящих, ни исходящих связей |
| `ParentAlsoExecutes` | предупреждение | блок с декомпозицией исполняется наравне с детьми |

Шесть последних правил добавлены не из общих соображений, а по результатам
атакующих тестов — каждое соответствует режиму отказа, воспроизведённому в
`tests/icom_attack.rs`.

Деление на ошибки и предупреждения: **ошибка означает, что граф будет построен неверно**
(потерянное ребро, паника маппера, недостижимая ветка); **предупреждение — что модель
исполнима, но, вероятно, неполно обследована**. Мёртвый вход родителя почти всегда
след незаданного вопроса на интервью, но останавливать из-за него пайп нечестно.

Каждое нарушение адресуемо: id блока, имя стрелки, тип правила отдельным значением
(`Rule`), а не строкой — вызывающий код принимает решение, не разбирая текст.

## Проверка на демо-модели

`examples_luck/horeca-model.json` (A1..A8) проходит без единого нарушения:

```
$ cargo run --bin validate -- ../examples_luck/horeca-model.json
OK: модель сбалансирована, нарушений нет
```

Дефект вносится одним символом — `picked_order` → `picked_order_TYPO` в выходе A4:

```
ОШИБКА DanglingInput A5 [picked_order]: стрелка «picked_order» блока A5 висит:
не приходит извне (ICOM блока A0) и не производится соседним подблоком
```

До валидатора эта опечатка молча давала граф без ребра A4→A5.

## Испытание на прочность (`tests/icom_attack.rs`)

Метод: не «проверить, что валидатор работает», а **пытаться его пробить**. Каждый тест —
гипотеза о дыре; проваленный тест означает найденную дыру, а не сломанный тест.
Первый прогон пробил валидатор шестью атаками из семи.

Два уровня проверки.

**1. Точечные атаки** — модель, которая обязана быть отвергнута: цикл, петля, дублирующий
источник, читатель ветки вне веток, сирота, исполняемый родитель. Плюс парный тест
`branch_target_consumer_is_legal` — законный случай, на котором тревоги быть не должно
(отдельная проверка на ложные срабатывания).

Отдельный тест `cycle_model_really_breaks_scheduler` доказывает, что найденный дефект
реален: циклическая модель действительно валит `Scheduler::run` с сообщением
«граф содержит цикл, не разрешимый обходом». Без такого подтверждения правило было бы
придиркой, а не проверкой.

**2. Два инварианта на случайных моделях** (детерминированный xorshift, без внешних
крейтов — падение всегда воспроизводимо по посеву):

- `invariant_accepted_model_always_executes` — **если валидатор не нашёл ошибок,
  планировщик обязан исполнить граф.** 3000 моделей: 1147 принято, все исполнились.
- `invariant_cycle_verdict_is_never_false_alarm` — обратная сторона: если модель
  отвергнута ИМЕННО за цикл, планировщик обязан на ней отказать. Проверено на 404
  моделях, ложных тревог нет. Ошибочный диагноз заблокировал бы работающий процесс —
  для валидатора это худший вид дефекта, хуже пропущенного нарушения.

Урок про сам генератор, стоивший двух итераций: **чисто случайные модели бесполезны.**
При узком алфавите потоков валидатор отвергал все 3000 подряд, и инвариант оставался
непроверенным (счётчик принятых = 0 поймал это; без него тест был бы зелёным и пустым).
Работает другая схема: корректная по построению цепочка плюс одна случайная мутация из
восьми реалистичных (опечатка в имени потока, цикл, петля, дубль, сирота, ветка в никуда,
пустая функция). Отсюда обязательное требование к таким тестам — **проверять, что обе
доли непусты**: тест, который ничего не принял, не проверяет ничего.

## Подключение

`icom::map_to_graph_checked(&model)` — обёртка над `idef0::map_to_graph`, проверяющая
модель ДО построения графа: `Err(violations)` при ошибках, `Ok((graph, warnings))` иначе.
Исходный `map_to_graph` не тронут — вызывающий код выбирает, нужна ли проверка.

## Второе применение: целостность SPAWN-подграфа

`icom::validate_spawned(&graph, &result)` — проверка постфактум, после `Scheduler::run`.

**Что удалось.** Аналог правила `DanglingInput`: порождённый узел не должен читать
идентификатор, которого никто в графе не пишет. Плюс предупреждение, если SPAWN породил
узлы, ни один из которых ничего не производит. Вендор не модифицирован.

**Чего не удалось и почему — это находка, а не недоделка.** Главное правило
(`MissingOutput`: подграф обязан произвести обещанный родителем выход) на SPAWN
перенести нельзя, и мешает этому не техника:

1. Техническое: `Scheduler::spawn` — приватная функция внутри `run()`
   (`vendor/luck-engine/src/scheduler.rs:415`), вклиниться в момент порождения нельзя
   без правки вендора, запрещённой проектной политикой. Это обходится проверкой
   постфактум — `run()` принимает `&mut IntentGraph`, финальный граф и
   `ExecutionResult::spawned` вызывающему доступны.
2. Принципиальное, и оно решающее: **узел SPAWN не объявляет ICOM ожидаемого подграфа.**
   Слот `PLAN` — свободный текст, а `INTO` принимает текст самого плана, не результат
   подграфа. Сверять «выход подграфа = обещание родителя» не с чем: обещание не выражено
   машинно-проверяемо.

**Что нужно в каноническом `tester-bcs/luck`.** Необязательный слот, объявляющий контракт
порождаемого подграфа, — по смыслу ICOM родительского блока, например
`EXPECT (produces=<ident>, consumes=<ident,...>)`. Тогда правило `MissingOutput`
переносится на SPAWN дословно, а нарушение становится `reject(VERIFY)` — узлом графа,
как требует Ядро. Это изменение уровня спецификации языка; здесь оно только зафиксировано.

Пока такого слота нет, у `SPAWN` есть гарантия синтаксиса (constrained decoding) и
гарантия объёма (`max_depth`/`max_nodes`), но **нет гарантии релевантности**: подграф
может быть безупречно каноничным, уложиться в бюджет и решать не ту задачу.
